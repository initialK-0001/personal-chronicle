# Brand-new TOKYO 対話記録の詳細設計

2026年11月19日・設計案。対象は本人が個人用ChatGPTで交わす会話。実装・配備・実際の会話の収集は開始していない。

## 1. 利用者から見た仕様

初回の連携以後、普段のChatGPTで新規・既存・再開したスレッドを使うだけで、「私」と「ChatGPT」の表示された発言を順番どおり自分だけの記録に残す。記録対象の選択、開始・停止、公開するかどうかの定期確認は日常操作に含めない。既存スレッドの新着は対象。連携開始より前の履歴は初回の遡及取り込みとして区別し、どの期間を取得できたか表示する。

管理画面に「対話記録」を設ける。日付（日本時間）、スレッド名、最初の質問の原文抜粋、状態で探せる。年月・本文検索・状態で絞り込み、一覧から選択した記録をまとめて公開または削除できる。1件を開くと発言者名と原文、対応する添付、取得できた発言日時を時系列で読む。非公開は保存完了状態で、公開待ちの通知を出さない。

| 操作・出来事 | 管理画面 | 公開サイト |
|---|---|---|
| 発言を受信 | 非公開で追加。受信途中と確定を識別 | 露出なし |
| 初めて「公開」 | 対象の発言・添付・タイトルをプレビューし、一括確定 | 選択した版を1記事として掲載 |
| 公開後に会話を再開・元の発言を編集 | 「公開済み・未公開の変更あり」。新着・編集を原本に保存 | 現在の公開版を表示 |
| 「続きを公開」 | 前回との差分を示し、選んだ範囲を確定 | 同じ記録のURLで更新。別の区切りの記録には別URL |
| 「非公開に戻す」 | 原文と区切りを保持 | 一覧・詳細・添付・検索から取り下げ |
| 「削除」 | 件名と対象件数を示して確認。本文・関連する全版・不要な添付を削除 | 公開中なら同時に取り下げ。ChatGPT側は操作しない |

## 2. 取得方法と実現可否

要件の対象はPCブラウザー、iPhone・iPad・Androidの普段使うアプリ／ブラウザー、および通常チャット・プロジェクト・Workの利用者に見える発言。PCで該当スレッドを開き直す操作も、発言ごとの転送指示も想定しない。「逐一」は各発言の原文が残り、未送信分も自動で追いつくこと。障害や端末のオフライン中に即時反映したように表示しない。

| 経路 | 使える範囲と採否 |
|---|---|
| 個人アカウントの履歴を自動で差分取得 | 本命。全スレッドの列挙、変更・分岐・添付へのアクセス、再開可能な差分取得、個人アカウントで許可された利用方法を確認できれば採用。現時点でこれらを満たす公開仕様は確認できていない。 |
| 手元のChromeで表示した会話の取得 | ブラウザーで見た発言に限る部分試作の候補。スマートフォンアプリだけで完結した会話や読み込まれていない過去発言まで揃うとは扱わない。画面からコピーできる見た目と元のMarkdownが一致するかも別に検証する。 |
| 公式のデータ書き出し | 過去履歴や欠落分を照合・補完する候補。設定等からの書き出し要求が必要。書き出し形式、分岐、Work、添付の収録範囲は実ファイルで確認する。書き出すたびに本人の操作が必要な方式は常用の自動記録要件を満たさない。 |
| OpenAI APIの会話・イベント通知 | 資料が説明するのはAPIで作成した会話とAPIのイベント。普段の個人用ChatGPTの履歴を取得できる根拠にはできない。 |

**採用判定**：本人の同意範囲内で利用できる取得経路を特定してから、専用の試験会話で下記の端末試験を行う。公式の経路を確認できない場合は「全端末自動取得は未成立」と記録する。非公開の内部API、認証Cookieのサーバーへの移送、要約からの復元に依存しない。一時チャットなど取得元で再読できない会話についても、回収を実証するまで対応範囲に算入しない。

確認した資料：[個人データの書き出し](https://help.openai.com/en/articles/7260999-exporting-your-chatgpt-history-and-data) ／ [APIの会話状態](https://developers.openai.com/api/docs/guides/conversation-state) ／ [APIイベントの通知](https://developers.openai.com/api/docs/guides/webhooks)

## 3. 保存単位・原文・区切り

- 原本の単位は発言。その上に「元スレッド」と「タイムラインに出せる記録区間」を持つ。各発言に親発言・取得元の順序を持たせ、受信順で無関係な枝を連結しない。再生成・編集で観測できた別の発言版は非公開で保持し、公開時は読者に見せる枝と版を固定する。
- 保存する本文は取得元の原文と書式。表・コード・改行・引用・リンク・絵文字・誤変換・訂正を維持する。受信できた表現の種類（元Markdown、本文テキスト、表示構造等）を記録する。本文と添付の表示順も保持。履歴に現れない内部指示・処理ログや未送信の入力欄は対象外。
- 新しい質問が直前の回答から **24時間以上** 空いたとき、その質問から別区間にする。初期設定案。回答が遅く届いても質問と対になる回答は同じ区間。元日時不明は取り込み時刻で分割せず、順序を保って管理画面で「日時不明」とする。取得元の日時と受信日時を別欄で持つ。
- 「ここから分割」「前回と結合」は管理側の区切りを変更し、原文と発言順を保つ。手で決めた境界を再同期で戻さない。公開済み区間の境界・タイトル変更は次の明示公開まで非公開。結合時は旧公開URLの扱いをプレビューし、公開確定時に後続側から統合先へ誘導。非公開区間の存在や名称を前後リンクから推測できないよう、公開側は公開済み区間同士だけを結ぶ。
- 公開タイムラインには区間ごとに1件。並び順・年月抽出は区間の最初の発言日時を使い、追記で先頭に上げない。元日時が全く分からない区間を公開する場合は掲載日を管理者が指定し、本文では元日時不明を維持する。

## 4. Xserver側のデータと読み出し

PHP/MySQLに専用テーブルを追加する設計。通常投稿の Store::content には300ブロック・JSON 900,000バイトの上限があり、長いスレッド全体を1投稿の下書きに格納すると継続記録が途中で止まる。対話原本は発言ごとに保持し、公開画面には確定した公開版を渡す。以下は追加予定の論理テーブル。

| テーブル | 主なキー・データ |
|---|---|
| dialogue_threads | 内部ID、連携元とアカウントを含む元スレッドキー（一意）、元タイトル、初出日時、最終受信日時 |
| dialogue_messages / dialogue_versions | 元スレッドと元発言キーで一意。親キー、順序、発言者、元日時、取得状態。版ごとに原文・書式・添付順・内容照合値。本文一致だけで別発言を統合しない |
| dialogue_segments / dialogue_members | 区間ID、スレッドID、表示タイトル、初出日時、手動境界、更新番号。区間内での発言順と選択した枝を保持 |
| dialogue_assets | 所属発言版、位置、元の表示名、取得状態、種別・大きさ、非公開保存先、内容ハッシュ。複数の参照がある場合の削除を管理 |
| dialogue_releases / dialogue_release_items | 区間と公開版番号、公開時点のタイトル・日時・明示選択した発言版と添付IDの順序付き一覧。区間が持つ現在公開版への参照が空なら非公開 |
| dialogue_sync / dialogue_deletions | 取得元別の確定位置・最終成功・再試行状態。削除済み発言は元キーの鍵付き照合値だけを保持し、再取り込みを抑止 |

公開一覧の既存経路（初期HTMLと /api/public/posts）には公開版から作ったカードだけを合流する。カードは公開専用ID、タイトル・原文抜粋（既存400字基準）、年月、公開済み画像の有無、個別URLを持つ。全文は個別ページでページ分割して読み出す。一覧での全文検索は公開版を対象にサーバーで検索し、検索結果のカードを通常投稿と初出日時順に統合してから表示件数を適用する。「画像を含む投稿」「文章のみ」も公開版で判定する。非公開の追記が検索・分類・サムネイル・サイトマップに影響しないこと。個別から一覧への復帰には既存の投稿位置復元を使う。

## 5. 受信・公開・削除の処理契約

| 操作（予定） | 処理 |
|---|---|
| 受信 POST /api/dialogue-ingest/batches | HTTPS、失効可能な取り込み専用資格で認証。公開・参照・削除権限は付与しない。入力は取得元、元スレッドキー、バッチ識別子、発言キー／親／役割／元日時／原文／書式／添付記述／確定状態。送信側が公開状態を指定する入力は拒否 |
| 受信確定 | 元キーで照合し削除済みチェック、版追加、区間割当を同一トランザクションで実行。本文確定と取得位置の更新を一体化し、コミット後に受領を返す。同じバッチの再送は同じ結果。識別子が同じで中身が違うバッチは競合。元の識別子が取れず照合が曖昧なものは非公開で隔離し、本文の無言の上書きや脱落を防ぐ |
| 添付受信 | 本文の確定と個別ファイルの完了は別管理。途中切断は再送し、照合値を検証してから参照可能にする。失敗時も発言内の元位置に「添付未取得」を表示。後着添付は非公開の新しい版に加え、公開内容への追加は明示操作。元画像・生成画像・その他のファイルを識別する |
| 管理 GET /api/admin/dialogues | 既存の管理ログインで認証。年月・状態・検索語・ページ位置で一覧を取得。詳細は発言順のページング。原本と公開中の版を比較可能にする |
| 管理更新 POST /api/admin/dialogues/{id}/{操作} | 公開、公開停止、分割、結合、削除。既存のAuth::mutationを使用。更新番号とプレビュー時の発言版集合を照合し、版の不一致は409。同時に届いた発言が意図せず公開されないよう公開版の参照切替を原子的に行う |
| 公開 GET /dialogues/{公開ID} | 現在の公開版を読み、表示用に安全に組版。公開版がないIDは404。公開添付もその公開版との関連をリクエストごとに検査。管理用と公開用の配信URLを分ける |
| 削除後の再同期 | 削除印と公開停止を先に同一トランザクションで確定し、本文・版・添付参照を消去。未参照ファイルの物理削除は再試行可能にする。削除印は発言単位とし、同じスレッドで後から行われた新しい発言は受け付ける |

取り込み側は未確認分を永続キューに残し、失敗時は間隔を延ばして自動再試行する。元履歴の照合が可能な方式では、確定位置の少し前から再走査して欠落と遅着を回収する。配信中の文字列断片は別発言として増殖させず、途中で終わった応答は取得できた部分と中断状態を保持する。端末が二つあっても同じ元キーで収束させる。新旧順を判定できない競合版は原文を両方保持して現行版を勝手に上書きしない。

## 6. 非公開・障害・復元

原本と添付実体は公開ディレクトリ外へ保存する。管理用の応答はキャッシュ保存を抑止し、公開停止後もアクセスを制御できる配信経路を使う。受信したHTMLやコードは本文として扱い、表示時にエスケープまたは許可した書式だけに変換する。保管用添付の原本と表示用の画像を区別し、大きすぎる画像を既存の公開画像登録に通すために原本を縮小して上書きしない。取得制限・容量不足・未対応形式は管理側で理由を示す。同期の記録には成功時刻・対象範囲・エラー種別を残し、本文、資格情報、期限付き添付URLはログに出さない。

管理画面には「最後に同期できた時刻」「取得できた範囲」「未取得の添付／中断」を表示する。一部端末にしか対応できていない段階で「全件保存済み」と表示しない。既存 Backup.php は対象表と復元形式を列挙するので、追加表・参照中の添付・削除印に対応する新形式と、旧形式を読み込む際の互換処理を用意する。バックアップは非公開領域に世代保存し、運用開始前に保管期限と鍵の復旧手順を決める。過去バックアップに残る削除済み本文は世代失効まで残る。復元前に最新の削除台帳を別保管先から取り込み、削除対象を除去してから配信・同期を再開する。

## 7. 実装順と合格条件

1. **取得経路の成立試験を先に行う。** 試験スレッドに異なる目印を入れ、PCのChrome、iPhone・iPad、Androidで新規と再開を確認する。PCを閉じ、スマートフォンのアプリだけで質問し、回答の終了後すぐ閉じる。後でそのスレッドをPCで開く・共有する・書き出す操作なしで、質問と回答がどちらも保存されるかを照合する。PC側が復帰後に無操作で回収する方式の場合は遅延と前提を記録。通常・プロジェクト・Workをそれぞれ判定し、書式・日時・添付・分岐の未取得は明示する。
2. **非公開保管を検証。** 合成会話に誤字、表、コード、同文を2回、添付、再生成を含める。原文と順序の比較、受領直前の切断、重複送信、2端末同時受信、容量不足、古い版の遅着を試験。未認証で一覧・検索・個別・添付・サイトマップに一切現れないことを確認。
3. **区切り・公開を検証。** 23時間59分、24時間ちょうど、深夜跨ぎ、日時不明、分割・結合・再同期を試す。質問と回答をまとめて公開した直後に次の質問を受信し、公開本文・抜粋・公開添付が変化しないことを確認。その後「続きを公開」で選択分だけ反映する。
4. **削除と復元を検証。** 公開・非公開をまとめて削除し、同一履歴と添付を再送。削除した範囲が全公開経路で消えたまま、新しい発言だけ非公開で入ることを確認。旧・新バックアップ復元でも削除台帳を照合する。
5. **稼働判定。** 動作を実測できた経路・端末・会話種別と遅延を管理画面に明示する。端末を問わず無操作で逐一記録する要件を、手動取り込みや一端末だけの結果で完了扱いにしない。
