## 0. 結論と今回の成果

「一つの投稿＝順序付きの画像と文章」を基本単位とする。最初に画像投稿・記事投稿などの形式を選ばせない。タイトルは空欄を許し、画像だけなら画像を、短文だけなら本文を主役にする。管理画面にも公開画面にも評価指標を持ち込まない。

現在の提案は **検索・テーマ・1列のタイムラインを中心とするタイムライン型UI**。初回A/B案は利用者から不採用の意向が示され、廃止した。DMMブックスなどのECサイトの見やすさを参考にするという希望を受けた再提案であり、最終承認済みではない。

今回の試作：総合・画像・文章切替、検索、テーマ別一覧、作品集のテーマ選択、投稿日時の降順、画像一覧／詳細一覧、個別表示、統合編集、サーバー下書き保存と復元、一覧への配置と再編集、下書きへの戻し、JSON書き出し。実広告・認証・コメントサーバー・本番DB・予約公開・外部アプリ接続は未実装。

最新の試作は認証付きサーバー保存へ変更。旧IndexedDBは書き出し用に残す。詳細は SERVER-STORAGE.md。試作保存先は本番保存先の決定ではない。見本画像は既存の公開ブログから取得した5ファイル。実際の新しい制作活動や感想を捏造しないため、見本文は試作用と表示している。

## 2. WordPress廃止・移行方法

### 方針

移行の一次資料は **DBダンプ＋ファイル全体＋WordPress書き出しXML（WXR）**。公開ページのクロールは照合用に使う。WXRだけでは画像本体や全設定が保全できない。WordPressを残したまま別環境で移行を反復する。

1. **原本確保**：DB、wp-content/uploads、テーマ・プラグイン、設定、.htaccess、robots、サイトマップ、広告設定を取得。秘密を含むバックアップは暗号化し非公開領域に保管。ソースリポジトリに入れない。
2. **復元試験**：取得したバックアップから隔離環境で旧サイトを復元。ファイルのSHA-256とDBテーブル・件数を記録。バックアップが存在するだけで成功としない。
3. **移行台帳**：旧ID、種別、状態、元URL、タイトル、元HTML、公開/更新日時、カテゴリ、タグ、添付・リンク・コメントの対応を記録。全ステータスを扱うが、公開用には公開済みだけを出す。
4. **変換**：安全に変換できる段落・画像・見出し等をブロック化。変換できない旧HTMLは消さず、原文を非公開で保持し、サニタイズした「旧記事互換」表示を用意。ショートコード・スクリプトを無条件実行しない。
5. **画像と添付**：原本・必要な派生ファイルをコピーし、バイト数・ハッシュ・画像寸法を照合。`src`、`srcset`、リンク先、CSS背景、ダウンロードファイル、CDN URLを抽出。縮小版しかない場合は警告し、原本取得済みと扱わない。
6. **URL**：可能な限り元のパスをそのまま解決するルートテーブルを作成。カテゴリ、タグ、添付ページ、ページ送り、フィード、`?p=ID` 等も調査。変更時は旧URL→新URLの一段301。無関係なトップへの一括転送はしない。
7. **比較**：投稿状態別件数、本文の正規化後比較と原HTML保存、添付ハッシュ、公開日時・タイムゾーン、内部リンクの行先、SEOメタ情報、canonical、構造化データ、RSS、サイトマップを照合。代表記事はPCとスマートフォンで目視。
8. **例外の解決**：ポーズ集、WordPress Download Manager、外部埋込、問い合わせ、旧コメントは個別の機能試験。未解決例外を移行完了として隠さない。
9. **切替直前**：必要な短い更新停止期間と差分取得を計画。切替時点の原本と新側のスナップショットを作る。切替・停止操作はユーザーの明示承認後のみ。
10. **切替・監視・戻し**：DNS切替が不要なら同一ホストのルーティング切替を優先。エラー、画像欠落、コメント漏えい等を運用ログで確認。障害時は旧配信へ戻し、新側に増えた投稿やコメントを別途保持してから差分調整する。

### 移行完了の条件

全件の移行台帳が「移行済み」または説明付きの保留に分類され、未説明の欠落ゼロ。公開対象・日時が一致し、全URLが期待する200/301/410等になる。添付原本のハッシュが一致する。下書き・未承認コメント・非公開画像を匿名取得できない。バックアップから復元できる。ユーザーが代表画面と例外を確認する。

旧WordPressの削除は、これらを満たした後でも別途承認が必要。切替後もしばらくは外部非公開の復旧用原本として保持する。

### 現在の試作

上部に検索、左側に表示対象とテーマ、中央に1列のタイムラインを配置。本文140字以下と画像1枚は一覧で全体表示。141字以上または画像2枚以上は省略して個別記事ページへ遷移する。投稿ボタンは管理画面だけに置く。ランキング・評価・人気指標は設けない。

## 4. 統合投稿・表示方式

### 内容のモデル

`Post` は `id`, `title: null|string`, `status`, `published_at`, `updated_at`, `revision_id` を持つ。内容は順序付き `blocks[]`。基本型は paragraph / heading / image / quote / link、後に gallery / comparison / legacy_html を追加する。

画像ブロックは画像ID、代替テキスト、説明、表示比率の希望を持つ。本文を生HTMLとして受け取り、そのまま実行する方式にはしない。見出し階層やリンクの装飾は構造化リッチテキストとして扱う。試作は枠を抑えた入力欄で順序付き要素を編集する簡易版で、インラインの太字・リンク指定等は第1段階の編集ライブラリで扱う。

### 自動表示の規則（提案）

- 画像あり・文章少量：画像主体。1枚なら全体表示、複数なら最初の1枚と個別記事への導線。
- 画像なし・短文：本文そのものを表示。空のタイトル領域を作らない。
- 長文／複数見出し：題名があれば題名、なければ冒頭文をリンクのアクセシブル名に使い、概要を短く表示。
- 作品表示：画像を持つ投稿を抽出。記事表示：意味のある本文を持つ投稿を抽出。双方に同じ投稿が出てよい。
- 自動判定が意図と違う場合だけ「代表画像」「概要」「見せ方」を任意設定。形式選択を投稿の入口にしない。
- 順序は原則公開日時。更新では自動的に先頭へ浮上させず、更新日を別に持つ。

試作品の現在の表示規則は末尾の最新仕様を参照。旧カタログ表示は廃止した。

### 保存・公開

本番は下書きの自動保存、画像アップロード、公開処理を分離。未完了のアップロード中は公開を完了できない。改訂版は非公開で編集し、明示的な「公開内容を更新」で公開版ポインタを差し替える。保存は改訂番号による競合検出を行い、別端末の内容を黙って上書きしない。

状態は draft / scheduled / published / private / archived。予約は明示指定された時刻にだけ公開。時刻はDBではUTC、UIでは日本時間を基本とする。公開版と編集中の下書き版を区別し、公開済みページの編集途中が漏れないようにする。

## 5. DB・画像・認証・広告の基本構成

### 技術構成の提案（契約確認前の条件付き）

第一候補は **エックスサーバー上のPHP＋MySQL互換DB＋独立した画像保管**。公開ページはサーバー側でHTMLを出し、管理エディタだけをTypeScriptで構築する。PHPの認証・セッション・入力検証は保守されているフレームワークに委ね、自作認証を避ける。Laravel等の適用可否は実契約のPHP/拡張/配備条件を確認して確定する。ビルドは開発環境で行い、本番にNode常駐を要求しない構成を優先する。

公式資料ではPHP8系、MySQL/MariaDB、cronが提供されるが、バージョンやバックアップ条件はサーバーによって異なる。ユーザー契約の機能を確認したとは扱わない。利用できなければ、別の汎用ホスト＋同じSQL/ファイル形式を第二候補とする。Sites専用のD1/R2を本番データの唯一の保存先にする案は採らない。

| 領域 | 提案 |
| --- | --- |
| 開発 | 今回は私用Sitesで静的試作。次に同じ構造のテストDB・画像領域を用意 |
| 公開 | 公開済み改訂だけをHTML/API/検索/RSS/サイトマップに出力 |
| 管理 | 別の管理経路。認証・権限検証を全操作で実施。表示を隠すだけにはしない |
| DB | posts、post_revisions、assets、post_assets、topics、post_topics、collections、collection_items、comments、legacy_routes、import_jobs、audit_events、admin_users、sessions |
| 画像 | 原本は公開ディレクトリ外。公開承認されたものだけ派生画像を配信。公開取消時は配信権限とキャッシュも無効化 |
| バックアップ | SQL＋原本＋メタデータJSON＋ハッシュ台帳。暗号化した別の保存先にもコピー。復元訓練を実施 |
| 検索 | 初期はSQLで題名・本文・テーマを検索。外部検索サービス依存は初期に増やさない |

`assets` はSHA-256、MIME、バイト数、幅高、保管キー、公開状態、派生元、代替テキストを持つ。`legacy_routes` は元URL/旧ID→新IDの一意対応。`comments` はpending/approved/rejected/spam/deleted、親コメント、公開可能な名前と本文、非公開の連絡先・不正対策情報を分離する。評価の数値を投稿スキーマに作らない。

### セキュリティとコメント

- 管理者登録は一般公開しない。パスワードの安全なハッシュ、TOTP等の追加認証、回復手段、試行回数制限を用意。
- セッションはサーバー側で失効可能にし、Secure/HttpOnly/SameSite Cookie、CSRF防御、ログイン時ID再生成、期限・ログアウトを適用。
- コメントPOSTは必ずpendingで保存。投稿者がapprovedを送っても無視。匿名GETはapprovedかつ公開済み投稿のものだけ。未承認内容・連絡先はレスポンス、HTML、ログ出力、検索インデックスに入れない。
- IP等に基づく有効期限付き頻度制限、ハニーポット、長さ・URL数制限、サニタイズを段階導入。必要になった場合だけ追加のボット対策を検討。
- 管理画面は承認・却下・スパム・保持型削除・任意返信。コメント数のバッジや人気比較は表示しない。
- アップロードは拡張子だけでなく実データの形式・寸法・容量を検証。画像再エンコードでEXIF位置情報等を公開派生画像から除去。SVG/HTMLは初期の画像アップロード対象にしない。
- 添付を推測しにくいURLにするだけでは非公開保護としない。下書き画像は認証を必要にし、バックアップ・旧HTML・エクスポートは公開領域外に置く。
- 外部画像取込は初期無効。将来追加時はSSRF、転送先、ローカルIP、容量の制限を実施。
- 依存の固定、脆弱性点検、更新手順、秘密情報の環境設定、DB最小権限、障害ログの個人情報削減を運用に含める。

### 広告・プライバシー

AdSenseを継続する前提で、長文の本文後・関連記事前、トップの投稿群の区切り等を候補とする。画像への重なり、鑑賞中の割込み、管理・下書きプレビューへの広告は禁止。広告枠の高さを予約し、レイアウト移動を抑える。作品詳細は作品と説明を読み終えた後の位置を基本とする。

収益維持は保証できない。既存ユニット・自動広告・除外領域を確認して継承し、広告停止や設定全廃を独断で行わない。収益やアクセスの数字をサイトの投稿管理画面に表示しない。

Googleの最新公式案内に従い、EEA・英国・スイスの対象配信では認定CMPなどの要件を確認する。広告、アクセス解析、コメント連絡先、IP等の不正対策情報の目的・保持期間・削除窓口を実運用に合わせてポリシーへ反映する。試作では広告リクエスト・アクセス解析を実行しない。法的な適用判断や広告アカウントの適合性を確認済みとはしない。

### 連携契約の提案

ファイル交換を第1の経路とし、APIは各アプリの実コード・認証方式を確認後に追加する。`schema_version`, `source_app`, `source_record_id`, `source_revision`, `captured_at`, `blocks`, `assets`, `provenance` を持つ受け渡し形式を定義する。これらの技術情報は編集者の画面には通常出さない。

1. 元アプリで本人が公開候補を選ぶ。
2. 必要な項目だけを非公開の取込領域へ渡す。個人メモ・位置・連絡先等は既定で除外。
3. 重複防止キーと出典IDで同じ取込の多重生成を防ぐ。
4. 画像の公開権・EXIF・本文・出典・公開予定範囲をプレビュー。
5. 本人が新サイトで公開を明示したときのみ公開版へ反映。

APIクライアントに `draft:create` 相当の権限だけを与え、`publish` を与えない。非公開基盤のDBを公開側から直接参照しない。元データの後日の変更を公開記事へ自動反映しない。

AI提案は第3段階。事実と出典を保持し、本人の体験や感想を補って創作しない。生成文はすべて下書き扱いで、AIによる公開操作は用意しない。

## 追補：日時と投稿単位の簡素化

最新の利用者指示を優先する。日時指定・予約公開は通常機能の要件から外す。1投稿は、一度一覧へ追加する画像と文章のまとまり。初回日時と更新日時はサーバーで自動記録し、一覧は初回日時の降順。旧記事の日時保全は移行専用の別処理とする。投稿内の画像・文章の移動は可能だが、一覧の並び替えとは区別する。

元サイトの実測色 #b4ffc0 / #f4f5f7 / #333 を採用。サイト操作文言の句読点省略、投稿本文の句読点保持は継続。


## 閲覧画面と管理画面の分離（2026-11-15）
- `/` は閲覧用画面。緑の表題部は画面幅いっぱいに表示。「自分の投稿」は削除し、すべて・画像・文章・作品集を左メニューに配置。幅800px以下では4項目を横並びにする。
- `/admin` は管理画面。下書き・投稿・調査と設計・ソース保存・投稿バックアップ・旧試作データ書出を集約。
- 閲覧用JavaScriptは保存済み試作データのAPIを呼ばず、公開見本だけを表示する。管理画面からの保存は外部公開を意味しない。本格的な公開機能は未実装。
- 管理画面・管理スクリプト・設計資料・ソースZIP・全APIをサーバー側で管理者認証する。Sitesの認証済みIDとメールを確認し、環境変数 `CHRONICLE_ADMIN_EMAIL` と一致する本人だけを許可。未ログイン401、他の利用者403、管理者設定欠落503。秘密情報の値をGitHubに置かない。
- Sites全体の閲覧範囲は本人専用のまま。一般公開への切替や既存WordPressの変更は行わない。
- Xserver移転時には独立認証を実装する。外部から任意指定された認証ヘッダーを信用しない。


## タイムラインと記事ページ（2026-11-15 最新仕様）
- PC・スマートフォンとも投稿日時降順の1列タイムライン。従来の複数列カタログと表示切替は廃止。
- 短文140字以下は全文表示。タイトル付き投稿または140字超の投稿は記事として表示し、画像があれば小さなサムネイルを左、タイトル・本文を右に配置。画像がない場合は画像枠も代替画像も作らない。タイトルなしの短い画像投稿は全体が見える縮小表示とする。文字数はタイトル・画像説明を除く本文要素（見出し・引用・リンク表示名を含む）の合計。絵文字等は見た目の1文字で数える。
- 141字以上は先頭140字、画像2枚以上は最初の1枚まで表示。いずれかの条件を満たす投稿は「続きを読む」または「投稿全体を見る」から専用ページへ遷移。
- 個別URLは閲覧用 `/?post=投稿ID`、管理用 `/admin?post=投稿ID`。直接アクセス・再読み込み対応。一覧での投稿閲覧ポップアップは廃止。管理エディタ内の公開前プレビューは継続。
- 作品集も通常ページとして表示。短文・単一画像の管理編集は一覧の編集ボタンから行う。
- 閲覧用は公開見本だけを表示する従来の試作範囲を維持。一般公開機能や移行作業には着手していない。
